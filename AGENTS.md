# AGENTS.md: technical notes for working on this project

User-facing setup is in README.md. This file is the technical record: how the firmware works, what was observed on the real hardware, how everything is verified, and what to watch out for.

## Working rules

- **Verify before touching hardware.** Every change goes through the host tests (`tools/run_tests.sh`, with `GUTENPRINT=1 AIRPRINT=1` for printing, IPP or HTTP changes, `WEB=1` for the web UI) and, when firmware behaviour changes, the QEMU self test (`tools/qemu_selftest.sh`).
- **Flash only with the user's go-ahead.** That includes OTA updates (`pio run -t ota`, `tools/remote.py upload`), reboots and the `panic` test. Reading `/info`, the remote log, the status pages and the serial log of a running board is fine.
- **Never read or print the secrets** in `.env` or the generated `src/local_config.h`. To check whether a key is set, test for a non-empty value without printing it, e.g. `grep -qE '^WIFI_SSID=.+' .env`. Reading a non-secret key (`HOSTNAME`, `MODE`) is fine.
- **Keep the core portable.** `components/canon_bjl`, `components/airprint` and `components/printers` build both natively (`host/`) and for the ESP32. Platform specifics go behind hooks or `#ifdef ESP_PLATFORM`.
- **Optimisations must not change output.** Pure speed changes must keep the reference CRCs below unchanged.
- **Don't edit a script while it runs.** bash reads scripts as it goes; an edit during `qemu_selftest.sh` broke a run with a syntax error.

## Configuration

- `.env.example` (committed) lists every key with its default. `.env` (git-ignored) overrides them, and is created from the example on the first build. Every key becomes `#define KEY "value"` in `src/local_config.h`. Keys: `WIFI_SSID`, `WIFI_PASSWORD`, `PRINTER_NAME`, `HOSTNAME`, `MODE`.
- `MODE`:
  - `normal`: printing.
  - `debug`: `normal` plus remote access (log, core dumps, OTA; see Debug mode). What the board runs now.
  - `dev`: fake printer (jobs converted and captured, nothing printed).
- `sdkconfig.defaults` holds all ESP-IDF settings; the qemu env adds `sdkconfig.defaults.qemu` through `board_build.cmake_extra_args`. The generated `sdkconfig.<env>` is git-ignored; delete it to pick up changed defaults. Notable settings: `-O2`, 32 KB I-cache / 64 KB D-cache, QIO flash, octal PSRAM (`SPIRAM_MALLOC_ALWAYSINTERNAL=16384`: allocations up to 16 KB stay internal), `LWIP_MAX_SOCKETS=28`, rollback bootloader, ELF core dump to flash, FreeRTOS trace facility (task list in `/info`).
- `PROJECT_VER` is set in `CMakeLists.txt`, because ESP-IDF's `git describe` fails in a repository without commits. The project name is `usb_host_probe` (OTA uploads must match it).

What the host tests cover:
- `bjl_host selftest`: encoder unit tests; every driver's test page against the direct `canon_bjl` one; the choice of driver for a device (`printer_driver_match`: USB ids, model names with and without " series", other makers); test page streams decoded by `bjl_decode.py`.
- `GUTENPRINT=1`: our encoder fed Gutenprint's ink planes must reproduce Gutenprint's stream byte for byte: the MG2500 at 300 and 600 dpi, Letter, 2 pages, and the same four for one Gutenprint model of each other stream variant (`compare_gutenprint.py --model`).
- `oled_host`: pixel layout, glyphs, scaling, clipping, UTF-8; then every screen (booting, no printer, ready, ink low, no paper, printing, printed, test page, failed, no WiFi) into `host/out/oled.png`. Look at it after any layout change.
- Web unit tests (`web/tests/*.test.ts`, run by node's type stripping, so `src/lib` files they import must stay plain TypeScript: no parameter properties, no extension-less imports): URF round trips (colour, gray, every packet kind, > 256 equal lines) against a decoder written from the format description, plus `raster_to_png.py` on the same output; the PDF writer (xref offsets, read back by pdf.js); layout (paper pixels equal canon_bjl's, rotations, fit inside the printable area); IPP encoding, JFIF dpi, auto-crop.
- `AIRPRINT=1`: ipptool IPP 1.1/2.0/Everywhere, printing URF/PWG documents rendered by macOS's own filters, cancel while printing; the web UI's files (gzip, 304), `/events`; the status screen drawn from the live state (`/dev/oled.pbm`) while printing and after the cancel (`oled-live-*` in `oled.png`).
- `WEB=1` (`web/tests/e2e.mjs`, playwright-core driving the installed Chrome): upload a PDF and a photo, print 2 pages at 300 dpi and the photo at 600 dpi (the jobs are decoded by `bjl_decode.py`), Process (rotate, ID card from a file, PDF export, viewer), the phone layout. Screenshots in `host/out/ui-*.png`; no page errors allowed. The CUPS sample files are gzipped on disk (ipptool unpacks them): the test unpacks them first.

What the QEMU self test covers (about 10 minutes):
- dry-run test pages (CRCs), IPP conformance, URF prints whose CRCs must match the host build; the web UI on port 80 (page, gzip asset, 304), `/api/state` and the first `/events` event;
- debug server: `/info`, `/log`, the live log; OTA: a non-image and a truncated image refused, an update rebooted before it confirmed itself rolled back by the bootloader, an update through `remote.py upload` confirmed; a deliberate crash: reset reason, crash summary in the log, core dump decoded by `remote.py crash` (finds `panic_cb`), erased;
- no display on the emulated I2C bus: reported, screen disabled, no `oled` task in `/info`.

QEMU setup: builds are at https://github.com/espressif/qemu/releases (`esp-develop-9.2.2-20260417`, `qemu-xtensa-softmmu-...-aarch64-apple-darwin`). That build only needs `/opt/homebrew/lib` (pixman, libgcrypt, SDL2); older builds also needed Homebrew's `libslirp` (`brew fetch libslirp`, unpack, add its lib dir to `QEMU_LIB_PATH`). macOS strips `DYLD_*` variables before they reach scripts, so the script sets them itself. Host ports forwarded: 18631 (IPP), 18000 (web), 18080 (debug), 12323 (log). A QEMU left running by an aborted run keeps those ports: kill it before the next run.

To try things on the Mac: `cd host && ./airprint_host` (port 8631), then http://localhost:8631/ (the web UI).

## The MG2500 on USB (observed)

```

  interface 0 alt 0: class ff/00/ff        scanner (not used)
    endpoint 0x07 bulk OUT, 0x88 bulk IN, 0x89 interrupt IN, max packet 64
  interface 1 alt 0: class 07/01/02        printer, bidirectional
    endpoint 0x01 bulk OUT, 0x82 bulk IN, max packet 64

  CLS:PRINTER;DES:Canon MG2500 series;VER:2.050;STA:10;FSI:00;HRI:D;...
port status 0x18 (selected, no error)
```

- The ESP32-S3 USB OTG port is full-speed only (12 Mbit/s, 64-byte bulk packets); the MG2500 falls back to it.
- `usb_printer.c` claims the printer interface at attach and logs the descriptors. One client, one device; a print job holds the `job_active` claim (`claim_device()`).
- USB-OTG VBUS: a spec-compliant printer only appears on the bus when 5 V is on VBUS, so the board's USB-OTG pads must be bridged.

## Printer drivers (`printer_driver.h`, `components/printers/`)

- A driver is a `printer_driver_t`: id, make and model, IEEE 1284 MFG/MDL, USB VID:PID (0 when unknown), colour, resolutions (the last is the default), papers (the first is the default), margins in 1/100 mm, `model` (the driver's own data); then the job (`job_begin(driver, io, dpi, paper)`, `page_begin(src_w, src_h, bytes_pp)`, `page_line(y, px)`, `page_end`, `job_end`, optional `job_stats`), an optional `test_page(driver, io, dpi, label)` and an optional `status(state, detail, data, st)` that maps the back channel's last status reply into IPP reasons, message and supplies.
- The driver writes through a `printer_io_t`: `write`, `sync(what)` (flush, then wait for the printer's reply to `what`; the platform waits 5 s, 180 s for "EndJob" if the printer answered "StartJob" (else 5 s), and carries on without a reply) and `progress` (test page: yield every 64 lines).
- `airprint.c` takes everything printer-specific from `airprint_config_t.driver`: IPP media, margins, resolutions, colour attributes, the URF string (`printer_driver_urf`, also in the mDNS TXT record), the paper of a job (`printer_driver_paper_for`: the driver's paper closest in height to the first page), the conversion. The host server picks the driver with `PRINTER_DRIVER=<id>`.
- Choice of driver on the board (`print_job_driver()`): when a printer is plugged in, `printer_driver_match` looks for a driver with its USB VID:PID, then one with its IEEE 1284 MFG and MDL (case and a " series" suffix ignored); that driver stays until another printer is plugged in (a printer switched off keeps it). Before any printer, and for an unknown one (logged), `CONFIG_PRINTER_DRIVER`. When the driver changes after startup, `airprint_esp_driver_changed()` updates the IPP make and model and device id and the mDNS records (removed and announced again). Printer-only models without a known USB id (iP2700, iP2800, P200) are matched by name only; their MDL strings are inferred from Canon's naming, not seen.
- Still Canon-specific outside the driver: `usb_printer.c` reassembles back-channel replies as IVEC XML (`</cmd>`) and fills `state`, `detail`, `data` from `GetStatusResponse`; the web UI's print dialog has A4/Letter at 300/600 dpi with canon_bjl's printable area (`web/src/lib/layout.ts`).
- Adding one: a Canon model whose stream is one of the `canon_bjl` variants is a `CANON_PIXMA(...)` line in `canon_pixma.c` plus its entry in `printers.c`. Another printer: a new source file in `components/printers/`, listed in `printers.c`, `components/printers/CMakeLists.txt` and `PRINTERS` in `host/Makefile`. Try it with `PRINTER_DRIVER=<id> host/airprint_host` (jobs land in `host/out/job-N.prn`). The board picks it by USB id or model name; `CONFIG_PRINTER_DRIVER` in `sdkconfig.defaults` only sets the default.
- `bjl_host selftest` checks that every Canon driver's test page is byte-identical to the direct `canon_bjl` test page of its model at every resolution; the reference CRCs below go through the driver on the host (AirPrint prints) and in QEMU (dry runs and prints, `canon-mg2500`, the default with no printer).

## Canon CAPT laser printers (LBP3300; `canon_capt.c`, `capt.c`, `hiscoa.c`): GPLv3

Seen on a real board (2026-11-05): `04a9:267e "Canon CAPT USB Device"`, one interface (class 07/01/02, bulk OUT 0x01, bulk IN 0x82, 64-byte packets), IEEE 1284 ID `MFG:Canon;MDL:LBP3300;CMD:CAPT;VER:2.1;CLS:PRINTER;DES:Canon LBP3300`, no scanner. Sending the MG2500's BJL stream to it does nothing: no `StartJob` reply, the printer never accepts data again until a soft reset.

- **License.** The CAPT files are GPLv3 (ported from captdriver); the rest of the project is MIT. `COPYING-GPL3` is the license text. Don't copy more captdriver code into MIT files.
- **Where the protocol comes from.** captdriver does not list the LBP3300; its LBP3000 job flow got as far as the printer accepting the page and then saying "paper out" without feeding (status word 0 bit 1 and word 1 bit 14, ~0.1 s after FIRE; every variation of the page parameters, of the E0A6 setup and of the flow gave the same). What fixed it is https://github.com/thientranvan/esp32_printer_canon_3300 (README, `print_test.py`, `mac_backend.pl`; its author watched Canon's own driver and printed on a real LBP3300): the **model key is 94 2A** (bytes 2-3 of the IDENT reply, not captdriver's 30 2A), the **paper source must be selected with `E1A9`** before every page and patched into the page parameters (byte 6), there is no `E0A6`/GPIO step in a normal job, and the image is a window inside the page (below).
- Protocol: a command is `[cmd lo, cmd hi, size lo, size hi] + data` (size includes the header), the printer answers most with the same header + data. **A reply can arrive in pieces** (IDENT: 6 bytes, then the other 58 of 64): `capt.c` reads until the size in the header is reached (1.5 s for the rest). `printer_io_t` has `flush`, `read` (one bulk IN transfer) and `delay` (< 0 on cancel) for that; `printer_driver_t.raw_io` tells the USB layer not to poll the Canon IVEC back channel (`usb_printer_set_raw`, `usb_printer_read`).
- Job (as Canon's driver and the reference do it): IDENT, status (`A0A8`), `START_0`, `JOB_BEGIN` (data `00 00 1E 00 00 00 00 00`; the reply holds the job id), job info `E1A1` (72 bytes, stage 1), `START_1/2/3` (`E0A3/E0A2/E0A4`: clear misprint, clear error, discard data), `E0A5` (`EE DB EA AD`, page 0, 16 bytes: go online). Per page: if it is the 3rd or later, wait for `page_printing >= page-2`; `E1A9` = `[size code, media 1, page width/2 LE16, page height/2 LE16, source 1, flag]` (A4: `02 01 B0 09 B3 0D 01 00`), the reply `00 01` is the selected source; one `D0A9` with the 40-byte page parameters (source patched), the HiSCoA parameters, two empty ones; the bands as `C0A0` packets of at most 4092 bytes (every 16th checks the status for "buffer full"); `C0A4`; wait for `page_decoding >= page`; `E1A1` stage 2, `E0A7` FIRE (page), `E1A1` stage 6 (the next page can follow at once). End of job: wait for `page_completed >= pages`, `E1A1` stage 4, `E0A9` (job id).
- Page parameters of an A4 page, 600 dpi (Canon's): `00 00 94 2A 02 00 [src] 00 | 00 00 00 00 00 11 04 00 | 01 01 02 00 00 00 | 78 00 78 00 | 50 02 | 76 1A | 60 13 | 66 1B | 00 00 01 00 00 00`: model key, size code 2, source, toner density 0, media 0, `11` = 600 dpi, margins 120 px (bytes 22-23 left, 24-25 top), **image = 592 bytes x 6774 lines starting at (120, 120)** in a 4960 x 7014 page, fuser mode 1. Letter uses the same layout with 5100 x 6600, 610 x 6360 and size code 0x0D: a guess, untested.
- Page data: 1 bit per pixel, 1 = black, 600 dpi (300 dpi is pixel-doubled), bands of 70 lines HiSCoA-compressed (`hiscoa.c`: long repeats + recent-byte cache + bit codes, every byte XOR 0x43; output a multiple of 4 bytes, an already aligned stream gets one more word of ones, as captdriver does). Input is dithered with an 8x8 ordered matrix on the luminance. Streamed: a band is compressed and sent as soon as its 70 lines are in, so no page buffer.
- **Two-sided printing** (the LBP3300 has a duplex unit; confirmed on the printer 2026-11-05, A4, 300 dpi: long edge and short edge, the back side upright after turning the sheet the right way). Each side is a page of its own for the printer. Byte 5 of the page parameters is the side: 0 one-sided, 0x02 front, 0x04 back (bit 0x08 there is the raster direction, which the E1A9 payload repeats). The **back is sent first**, then the front, each with its own E1A9, D0A9, data, `C0A4`, `E1A1` stage 2, FIRE, `E1A1` stage 6; the printer prints both sides of one sheet. **The printer's `page_out` / `page_completed` counters count sheets** (a front counts, a back does not): after two sides they read 1, not 2 (waiting for 2 made the job hang until it timed out, and the status looked like "paper out"); `page_decoding` / `page_printing` count sides. AirPrint, PWG raster and the web UI send front, back, front, ... so the driver **holds the front** (compressed bands in the job's big buffer: `printer_io_t.big_buffer`, the shared 7.5 MB PSRAM buffer taken by `airprint_esp.c:job_buffer` and given back in `job_close`) until the back is there. A last odd side goes out one-sided (flag 0); a one-sided page after a held front prints the front first, one-sided. Without a big buffer (no PSRAM) the pages print one-sided.
- **Orientation.** Pages arrive upright, back sides too (URF `DM1` in `urf-supported`, `pwg-raster-document-sheet-back` normal, what the web UI sends). The printer prints a back as it gets it, upside down when the sheet is turned over the long edge, so for the **long edge the driver turns the back by 180 degrees** (`BACK_ROTATE_LONG 1`: the rows reversed, each row's bits reversed, `rotate_row`; the image window is 120 px from the left and top but 104 px from the right, so the raw back is rendered from the page columns starting at 104, `set_window`) and for the short edge it does not (`BACK_ROTATE_SHORT 0`). A rotated back is held raw (592 x 6774 bits = 4 MB) at the end of the big buffer and compressed at its end; the held front shares the rest (a front that does not fit fails the job). Switch at run time with `POST /capt?o=40&v=0|1` (long edge) or `o=41` (short edge), `?clear=1` removes the override.
- **The two sides are not registered alike** (measured 2026-11-12 to 2026-11-18, A4, long edge, `duplex_lines.py`: vertical lines 30 mm from each page edge; 300 and 600 dpi behave the same). With Canon's left margin of 120 px on both sides the front prints 8 mm too far left (22 / 38 mm) and the back within 1 mm. The printer places a window at its left margin (bytes 22-23), 1 px for 1 px, so the front's window starts `FRONT_SHIFT_PX` (188) further right and `BACK_SHIFT_PX` is 0: both sides then measure 30 / 30 mm. **The page columns a window shows must not move with it** (`set_window`: they start at the nominal margin): moving both cancels out, and margins 120, 220 and 320 done that way printed at exactly the same place. The window has to end at least 8 px before the page edge, so the front is 580 bytes wide and loses what lies within 8.5 mm of the right edge (Canon's window: 4.4 mm). Run-time overrides: `POST /capt?o=43&v=<hex>` (front), `o=44` (back), signed bytes in units of 4 px; on a turned back a positive value moves the image left as seen after the turn. One-sided pages are not shifted and their position is not measured; short edge and Letter are not measured either.
- Where the mode comes from: the URF page header byte 2 (1 one-sided, 2 long edge, 3 short edge) or the PWG raster header (Duplex at 272, Tumble at 368), as `raster_page_t.duplex`; `printer_driver_t.duplex` makes IPP advertise `sides-supported` one-sided / two-sided-long-edge / two-sided-short-edge and `DM1`, and `page_options(job, mode)` tells the driver before each page. The status JSON has `"duplex"`; the web UI's print dialog shows a Sides choice (one-sided, two-sided long edge / short edge) when it is true, sets the URF header and the IPP `sides` attribute, and adds a blank back to an odd page count so that the next copy does not start on the back of the last sheet (`web/src/lib/print.ts`, `urf.ts`, `PrintDialog.svelte`, `web/tests/duplex.test.ts`).
- **The printer goes offline between pages** (found 2026-11-08 with a 600 dpi PDF printed from the web UI, which renders a page in 5-12 s: only the first sheet came out). When the printer has printed everything it was given it goes offline: status word 0 reads `8E12` (bit 4 and the "no paper" bit 1; bit 0 later), word 1 `0201`, instead of `8E00`. A page sent then is received but never decoded (`page_decoding` stays), and the printer looks "out of paper" with a full tray; the driver gave up after `DECODE_MAX_S`. The same state is what the printer is in before a job's start-up steps. Quick test documents (all pages within a few seconds) never show it, because the next page arrives while the last one is still printing. `page_prologue` therefore reads the status before each page after the first and, if bit 4 is set, repeats `E0A3 / E0A2 / E0A4 / E0A5`; **the printer's counters then start again from 0**, so the driver counts pages and sheets from `pg_base` / `sheet_base` (the numbers it sent before the restart). The restart is only done when nothing is in progress (`page_decoding == page_printing`, `page_out == page_completed`): a `9E12` seen right after a page was started (2026-11-10) was restarted, which lost the page, and the printer then refused every job until it was switched off. Such a refusal of `JOB_BEGIN` (reply `87 00`, every later command `88 00`) means a job of an earlier session is still open; `job_prologue` tries `E0A9` with ids 1 to `STALE_JOB_MAX` and begins again (tested on `capt_host` only, not on the printer). The server also drops a job that sends nothing for 15 s (socket timeout). Test: `capt_host` (`offline_after`), and on the printer `duplex_gap.py` (a 4-side document with a pause before the 3rd side; 12 s works, 25 s is cut by the server).
- **Out of paper in the middle of a job** (2026-11-08, tray emptied on purpose, 300 dpi two-sided test and a 600 dpi PDF). Status when the next sheet cannot be fed: word 0 `xx06` (no paper bit 1 + buffer full: the page is decoded and waits), word 1 bit 14 (`4000`); a few seconds later bit 4 as well (`9C13`/`9E17`, word 1 `4000`). Only both "no paper" bits count as paper out (`8E12` with word 1 `0201` alone is the idle-offline case above). The paper sources (`A0A1`, reply: 18 bytes of header, then 16-byte records; record 1 = cassette 1) show the tray: first byte `A2` empty / `E2` paper present (bit 0x40), last field `0000` / `FD00`. **After loading paper the printer does not go on**: the sensor reads `E2` but the status words stay exactly the same, and neither the button, opening the top cover, pulling the tray out, nor `E0A2` / `E0A3`+`E0A2` / `E0A2`+`E0A5` / all three / `E0A6`+`E0A2`+`E0A5` changes anything (the reference project saw it print on after loading paper and closing the tray; not here). Only switching the printer off and on helps, as after a jam, and the job is lost. So the driver waits `PAPER_MAX_S` (300 s) for paper, reporting `media-empty-error` / "Out of paper" (the `status` hook, `canon_capt_paper_out()`) meanwhile, and then fails the job. The wait is also done before the restart of `page_prologue` (a restart clears the flag but not the cause). While waiting, `paper_probe` reads `A0A1` every 3 polls (logged) and runs a recovery step chosen at run time, `POST /capt?o=42&v=N` (1 `E0A2`, 2 `E0A3`+`E0A2`, 3 `E0A2`+`E0A5`, 4 all, 5 `E0A6 01 00`+`E0A2`+`E0A5`): kept for trying more ideas. Tests: `capt_host` "no paper" and "offline, no paper".
- Cancel / failure: a cancelled page is finished with white lines (the sheet is ejected) and the job closed; after an error the printer is cleaned up the way Canon's driver does it (`E0A6 01 00` go offline, `E0A3/E0A2/E0A4`, `E0A5` page 0, `E0A6 01 00`, `E1A1` stage 4, `E0A9`), then the platform's soft reset.
- Status words (captdriver's SPECS 1.3): `A0A8` reply data bytes 0-1 STATUS0 (bit 7 busy, bits 4-5 uninitialised, bit 2 buffer full, bit 1 paper out), 8-9 STATUS1 (bit 14 paper out, bit 7 processing data), 14/16/18/20 the page counters decoding/printing/out/completed. The reference also reads `A0A1` (8 records of 16 bytes, one per paper source: bit 0x80 installed, 0x40 has paper); not used here yet. Nothing reads the toner level or maps the status to IPP reasons yet (`status` hook NULL: the web UI shows "Ready").
- **No scanning at all** (removed 2026-11-18: the only printer in use, the LBP3300, has no scanner). `components/scanner` (pixma protocol, JPEG encoder, `/scan` and `/eSCL`), the USB scanner interface, the Scanner page and the `_uscan` record are gone; they are in the git history up to `7a647cb`. `shared_buf.c` stayed and moved to `components/airprint`. The button's single press does nothing now. A file saved as a scan by an older version stays in the browser's Files and keeps `source: 'scan'`.
- Debugging aid: `POST http://<board>:8080/capt?o=<byte 0-39>&v=<hex>` overrides a byte of the page parameters for the next pages, `?clear=1` removes the overrides (`canon_capt_set_override`). A probe script that set them, printed, watched the status after FIRE and cancelled was how the dead ends above were ruled out.
- Tests: `host/capt_host.c` (`make -C host capt_host && host/capt_host selftest`; part of `tools/run_tests.sh`): HiSCoA compress/decompress round trips, and the driver against an emulated CAPT printer that parses the stream, answers status requests (busy, buffer full, replies in pieces), requires `E1A9` and the patched source/key/margins, decompresses the bands into the page it would print and reports any protocol violation. It checks black and white pages pixel by pixel at 300/600 dpi, A4/Letter, gray and RGB input; halftone density; two pages; cancel; a silent printer. Two-sided: the order and flags of the sides, the sheet counters, both rotations pixel by pixel, 3 sides (odd), 4 sides on Letter, mixing one- and two-sided pages, no big buffer. The emulation is written from the documented conversation: it shows the driver does what it means to. Reference: test page at 600 dpi, CRC-32 of the PRINT_DATA payloads `d211cf6d` (97 packets). `host/capt_host testpage out.pbm` writes what the emulated printer prints.
- On the board: `usb_printer_set_raw()` is called from `print_job_set_printer`; the status read already pending at attach is cancelled then. A one-sided A4 test page at 300 dpi took 14 s from the first command to the end of the job, a two-sided sheet about 18 s; a job's log shows every command and reply (`capt` tag).
- The Windows PC used for this had no C compiler: the host test was built with `python -m pip install --user ziglang` and `python -m ziglang cc ...`; PlatformIO was installed with `pip install --user platformio` (set `PYTHONUTF8=1`: its output has characters cp1252 cannot encode). Building without WiFi settings in `.env` works: `src/wifi.c` then uses the network the WiFi driver saved in flash (a USB flash does not erase it).

## Printer protocol (MG2500 series)

- No page description language: Canon BJ raster commands wrapped in IVEC XML. Sources: Gutenprint 5.3.5 `print-canon.c` (the MG2500 series is the "PIXMA MG2400" model there, model 8002400) and Canon's cnijfilter 4.00 (model 423), which uses the same IVEC operations.
- Job: `StartJob` XML, `ModeShift` XML. Then per page: `ESC [K` reset (first page only), page setup (`ESC (b (q (d (t (c (p (P (T (l (v`), multiraster mode (`ESC (I`, `(J` 8 lines per block, `(L` "CMYK"), and `ESC (F` blocks of PackBits lines, each line terminated by `0x80`, one block per ink per 8 lines. A page ends with FF and `ESC (b 0`. The job ends with `ESC @` and the `EndJob` XML.
- Modes (Gutenprint's MG2400 table):
  - `600x600dpi`: C/M 2 bits per pixel with 3 levels, Y/K 1 bit
  - `300x300dpi`: CMYK all 1 bit
- Paper: A4 (`ESC (P` size `0x03`, 4961×7016 in 1/600") and Letter (`0x0d`, 5100×6600). Borders are 10/10/9/15 pt (left/right/top/bottom).
- Our streams are byte-identical to Gutenprint's, except Gutenprint drops a page's last 8 lines when the height is a multiple of 8 (`canon_write_multiraster` never flushes that block).
- Other models (`bjl_model_t` in `canon_bjl.h`, found by rendering every Canon family in Gutenprint 5.3.5 and comparing it with the MG2500's stream): these send the same XML, modes, inks and raster blocks, and differ only in the page setup. Gutenprint's caps behind each difference: `ESC_P_len`, the `ESC (P` tray byte (`0xff` for these models), `ESC_l_len`, `CANON_CAP_v`, `CANON_CAP_w` (`ESC (w 00`, first page only) and the `control_cmdlist` (an `ESC [K 00 1f` + `BJLSTART\nControlMode=Common\n<cmd>\nBJLEND\n` block before the first reset).

  | variant | `ESC (P` | `ESC (l` | `(v` | `(w` | BJL | series |
  |---|---|---|---|---|---|---|
  | MG2400 | 9 bytes, last `00` | 3 | yes | | | MG2400, MG2500, P200 |
  | MG2900 | 9, last `ff` | 2 | yes | | | MG2900, MG3000, E470, E460 |
  | iP2800 | 9, last `ff` | 3 | yes | | | iP2800 |
  | E3100 | 9, last `ff` | 2 | yes | yes | | E3100, TS3100 |
  | MP230 | 9, last `00` | 3 | | | | MP230 |
  | iP2700 | 6 | 3 | | | `SetSilent=OFF` | iP2700, MP250, MP270, MP280, MP490, MP493, MP495, MX340, MX350, MX360, MX410, MX420 |

  Only the MG2500 was tried on paper. Whether the older ones (iP2700 variant, 2010) answer the IVEC status requests is unknown. Next candidates (2-bit black at 600 dpi, otherwise header bytes): MX370/430, MX390/450, MX470, MX510, MX520, MX530, E500, E510, E560, E600, E610, MG3500.
- Back channel: when read, the printer answers with about 1 KB of `GetStatusResponse` XML (status, `status_detail` such as `MarkerSupplyAttention`, Canon fields such as `CIR:CL=000,BK=UK` for ink), e.g. `idle (MarkerSupplyAttention) BST:04;...;CTK:CL,LOW,/,BK,SETZ; CIR:CL=000,BK=UK;...`. Poll it at most every 2 s when idle and every 250 ms during a job, and reassemble replies from the 512-byte reads. Like Canon's driver, we wait up to 5 s for the `StartJob`/`ModeShift` replies and up to 180 s for `EndJob` (the page is done), and carry on if a reply never comes.
- Cancel: stop at a line boundary, finish the page (eject) and end the job. If the printer stops accepting data, after 8 s abort the transfer and send the printer-class SOFT_RESET.

## Web UI (`web/`)

- Svelte 5 (runes) + TypeScript, built by Vite into `web/dist`, packed into the firmware by `tools/gen_web.py` (each file gzipped, about 590 KB in all; the firmware is 1.67 MB of the 4 MB slot) and served by `components/webui` with `Content-Encoding: gzip`, an ETag (304 on `If-None-Match`) and `immutable` caching for the hashed `/assets/` files. The app (51 KB gzipped) loads pdf.js (156 KB + the worker, 1.3 MB raw, legacy build for older Safari) only when a PDF is opened. It works with no internet access. Without Node.js and without `web/dist`, the table is empty and the server shows its plain status page at `/`.
- Layout: a left navigation (Printer, Files, Process) with live status lines; under 760 px wide the navigation is the first screen and a section opens full screen with a back arrow (hash routes `#/printer` etc., so the phone's back works). Light and dark themes.
- Live state: `EventSource('/events')`. The server keeps one JSON snapshot (`{"printer":...}`, built every second by `events.c` from `airprint_status_json`) and sends it when it differs from the last one; a keep-alive comment every 15 s. The listener's socket is handed over (`airprint_http_detach`) to one hub thread, so it uses neither a connection slot nor a thread; at most 4 listeners (the oldest is dropped), a listener whose send buffer is full is dropped, and EventSource reconnects (`retry: 2000`). Server-Sent Events rather than WebSockets: the data only flows to the browser (commands are plain requests), and it reuses the HTTP server (no SHA-1 handshake, no framing). The printer status inside costs a USB control transfer, so it is cached for 2 s.
- Files: IndexedDB (`printer-web`, stores `files` and `kv`) in each browser, nothing on the device. Each file keeps its blob, a JPEG thumbnail, its pages (PDF), pixel size and dpi (JFIF / PNG pHYs, below 75 means unknown). The tab groups files by day (local date of `created`, newest first: Today, Yesterday, "Mon, 28 Sep"); Select mode numbers files in the order they are picked (a day's check picks the whole day) for Delete or Save as PDF: every page of the picked files, in that order, through the Process export at their own size ("as cropped", 200 dpi; PDF pages are rasterized).
- Printing: the browser renders the pages and sends URF over IPP to `/ipp/print` (port 80), so the device only sees what AirPrint clients send. A page is drawn in bands of about 2.5 Mpx (phones cap a canvas near 16 Mpx; A4 at 600 dpi is 35 Mpx): pdf.js renders each band with a translation, images are drawn with `drawImage`; bands outside the content are white without drawing. `urf.ts` compresses the lines (line repeats, runs, literals, "rest is white"); pages are kept as Blobs, copies reuse them. The request goes through `XMLHttpRequest` for upload progress (streamed request bodies need HTTP/2 in browsers), whose pace is the printer's since the server prints while it receives; the response comes when the job is done. Sizes seen: the 2 first pages of `document-a4.pdf` at 300 dpi 7.1 MB, a 512 x 768 photo on A4 at 600 dpi 10 MB. Options: copies, page ranges, A4/Letter, fit (inside the printable area) / fill / actual size, orientation (auto turns landscape content a quarter counter-clockwise), colour or gray (sgray), 600 or 300 dpi. Files saved as scans by an older version default to actual size, everything else to fit.
- Process: a workspace (`kv.workspace`) of items: a page (file, page, rotation, crop normalized in the rotated page) or an ID card (front and back crops, landscape or portrait). The crop editor locks the card's shape and has an auto-detect (`autocrop.ts`: the box of pixels that differ from the border's median, ignoring specks). ID card: a picture of each side from Files, cropped around the card; both go on one A4/Letter sheet at 85.6 x 54 mm, in the upper and lower halves. Export: each sheet is rendered at 150/200/300 dpi, JPEG-encoded and written by `pdfwriter.ts` (pages of DCTDecode images); page size A4, Letter (landscape pages get landscape sheets; real size when known and it fits, else as large as fits) or "as cropped".
- http:// on the LAN is not a secure context: no `crypto.randomUUID`, Web Locks, service workers or clipboard writes. IndexedDB, Blob URLs, workers and EventSource work.

## AirPrint / IPP and the HTTP server

- One server (`airprint.c`), two listening ports: 631 for IPP (and the pages), 80 for browsers (`web_port`; the mDNS `adminurl` points there). Port 80 also accepts IPP.
- Routing: POST to `/` or `/ipp*` is IPP; other POST and DELETE requests go to the `http_handler` hook (which may read the body with `airprint_http_read_body`; the rest is drained after it), GET/HEAD go to the hook first and then to the built-in pages (`/`, `/icon.png`). Response helpers: `airprint_http_send(_ex)` (extra headers such as `Location`), chunked `airprint_http_stream_begin/write/end` (30 s send timeout; plain close-delimited for HTTP/1.0), `airprint_http_host`, `airprint_http_if_none_match`, `airprint_http_detach` (the socket is the caller's from then on; the connection slot is freed). The platforms chain the hooks: `events_http || webui_http`.
- mDNS: `_ipp._tcp` on port 631 with the `_universal` subtype (needed by iOS) and `_print` (IPP Everywhere). The TXT record follows Bonjour Printing, with `URF=V1.4,CP1,W8,SRGB24,RS300-600,MT1,PQ3-4-5`, `air=none`, `Scan=F`. `CONFIG_MDNS_MAX_SERVICES=4`.
- Operations: Print-Job, Validate-Job, Create-Job, Send-Document, Cancel-Job, Cancel-My-Jobs, Close-Job, Get-Job-Attributes, Get-Jobs, Get-Printer-Attributes, Identify-Printer (flashes the LED blue).
- Formats: `image/urf` and `image/pwg-raster` (8-bit sRGB or sgray, 300/600 dpi, sniffed for `application/octet-stream`). The page's dpi picks the printer mode, and its height picks the paper (under 11.35 in means Letter).
- Pipeline: socket -> raster decoder (one line at a time) -> `bjl_render` (crop to the printable area, sRGB -> CMYK with full black generation `C = (c-k)/(1-k)`, dot gain curve, ordered dither) -> `canon_bjl` -> `job_write` hook. One job at a time; a second one gets `server-error-busy`.
- iOS flow seen on hardware: Validate-Job, Create-Job, then Send-Document with URF at 600 dpi colour. No IPPS was needed.
- HTTP: keep-alive, chunked bodies, `Expect: 100-continue`. Unread document data is always drained before replying: closing early resets the connection, the client loses the response, and libcups retries the whole job.
- iOS keeps several keep-alive connections open while it watches a job, so the limit is 8 connections with a 15 s idle timeout. Refusals are logged.
- Status mapping: `MarkerSupplyAttention` becomes `marker-supply-low-warning`. The `CIR` field gives ink levels (`UK` means unknown). The port status "paper empty" bit becomes `media-empty-error`. The names used for jam and cover open are guesses (never seen on hardware).
- Conformance (ipptool): IPP 1.1 and 2.0 pass everything, and IPP Everywhere passes all but `image/jpeg`. Results are the same on the host, in QEMU and on the board.

## Debug mode (`MODE=debug`)

For a board left at the printer without a USB cable: normal printing, plus (`src/debug.c`, driven by `tools/remote.py`):

- HTTP server (`esp_http_server`, port 8080, 3 sockets, 12 URI handlers; the default of 8 is too few): `GET /` (help), `/info`, `/log`, `POST /ota`, `/reboot`, `GET /coredump`, `POST /coredump/erase`, `POST /loglevel?tag=&level=`, `POST /panic`. Live log on TCP 2323 (one client at a time; `nc <host> 2323`).
- Log: `esp_log_set_vprintf` copies every line (cut at 255 chars) into a 64 KB PSRAM ring (started first thing in `app_main`). The last 3 KB also go to RTC memory (`RTC_NOINIT_ATTR`, survives panics, watchdogs and software resets, not power loss) and open the next boot's log as "end of the previous boot's log", followed by the reset reason. A PSRAM noinit segment is not possible: it conflicts with `SPIRAM_IGNORE_NOTFOUND`, which QEMU needs.
- Crashes: ELF core dump to the `coredump` partition (128 KB at 0x820000); the next boot logs the crashed task, PC and backtrace; `remote.py crash` downloads the dump and decodes it with `esp_coredump` (PlatformIO's Python) and `xtensa-esp32s3-elf-gdb` (found in `~/.espressif/tools`); it needs the `firmware.elf` of the build that crashed (`--elf`). `remote.py panic` crashes on purpose (null write in a timer callback).
- OTA: `POST /ota` with `firmware.bin` (the image is checked: ESP32-S3, project name, then `esp_ota_end` validation), refused while printing (409), written to the other slot, then a restart 1 s after the reply. Rollback (`CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE`): a new image stays "pending" until `debug_ota_confirm` sees WiFi and the debug server up for 20 s (run in every mode, so an image that switches mode is confirmed too); any reset before that, or 180 s without, brings back the previous image. The rollback bootloader marks the image it first boots (USB-flashed) valid.
- `/info`: version, `elf_sha256` (first 8 bytes of the image's ELF SHA-256, formatted from `app_elf_sha256`; `esp_app_get_elf_sha256` is limited to 9 chars by `CONFIG_APP_RETRIEVE_LEN_ELF_SHA`), mode, partition, OTA state, next slot, uptime, `boot_id` (random per boot), reset reason, internal and PSRAM heap, RSSI, core dump, task list with stack high-water marks.
- `remote.py upload`: reads the ELF SHA from the image (offset 32 + 144), uploads, waits for a new `boot_id` (uptime comparisons failed in QEMU), then for `ota_state valid`; reports a rollback if the old build comes back. `REMOTE_HTTP_PORT` / `REMOTE_LOG_PORT` redirect it (QEMU tests). An OTA of the 1 MB image takes about 11 s; the whole `pio run -t ota` with the confirmation about 45 s.
- No authentication: anyone on the network can update the firmware. An image built with another MODE has no OTA: the next update needs USB.
- The bootloader and the partition table only change with a USB flash.

## Status screen (`oled.c`, `components/oled`)

- Optional 128x64 I2C OLED: SCL GPIO41, SDA GPIO42 (Kconfig `OLED_*`; GPIO 39-42 are the pad JTAG pins, unused while JTAG goes over USB), 400 kHz, internal pull-ups on top of the module's. SSD1306 by default, `CONFIG_OLED_SH1106` for 1.3" modules (column offset 2), `OLED_FLIP` for a module mounted upside down. Address 0x3C, else 0x3D.
- A task (4 KB stack, priority 2) gathers the state every 250 ms (`airprint_get_activity`: the cached printer status and the running or last job with the page's progress; WiFi IP and RSSI), draws it with `oled_ui_render` and sends only the 128-byte pages that changed (page addressing on both controllers).
- Priority on screen: a print job, the local test page, a result (printed / canceled / failed) for 60 s, no printer, a printer problem (paper, jam, cover, ink) as the headline, else READY with the message and ink bars.
- The bus is probed at boot (0x3C then 0x3D, 3 tries 50 ms apart). No display: logged, the I2C bus deleted (GPIO41/42 released) and no task started, so a screen plugged in later needs a reboot. A display found at boot that stops answering (a failed transfer) is probed again every 5 s.
- Sleep (burn-in): off after `OLED_SLEEP_MIN` (10) minutes with the same picture (the WiFi bars don't count); any change or a button press turns it on. `oled_wake()` (at press-down) returns true when the screen was asleep: that press is swallowed (no double press or cancel), so a press on a dark screen never starts anything. Without a display it returns false and the buttons work as usual.

## Buttons (`main.c`)

- All active low with the internal pull-up, polled every 10 ms, 30 ms debounce. BOOT (GPIO0) and `PRINT_BUTTON2_GPIO` (GPIO4) are ORed into one button: double press (400 ms) = test page, hold 2 s = cancel the running print; a single press only logs a hint.
- `USER_BUTTON_GPIO` (GPIO5): debounced, wakes the screen, then calls `on_user_button()`, which only logs. Deliberately unassigned, for forks to give it a feature. -1 disables either extra button.
- GPIO4/5: no strapping, PSRAM, flash or other use (the parked SD card plan uses 9-14).
- On the board the display answers at 0x3C; the picture is not yet confirmed by eye.

## Dev mode (`MODE=dev`)

`airprint_esp.c` swaps the printer hooks for a fake printer: always ready, jobs converted and checksummed, the printer data kept in the shared buffer (if it fits) and served at `http://<host>/dev/last-job.prn` (decode with `tools/bjl_decode.py --png`). The USB host still runs.

## Performance and memory (ESP32-S3 @ 240 MHz)

- Printing an A4 page: 300 dpi about 2.2 s, 600 dpi about 8 s (text) or 9 s (photo). The MG2500 needs 7.5 s or more per page. Each job logs its time split (network / output / render / decode) and the CPU cycles per render stage.
- What mattered for printing, in order:
  1. Pass white lines as `NULL` from the decoder and fill runs in bulk.
  2. A tight white-skipping loop, with the CMYK conversion `noinline`. At `-O2` GCC hoisted the conversion above the white test and spilled registers, costing about 50 cycles per white pixel.
  3. Skip dithering inks that have no coverage, skip all-zero groups of 8 pixels, and dither only the inked span.
  4. `-O2` (ESP-IDF defaults to `-Og`), IRAM for hot functions (`BJL_HOT`), 32 KB instruction / 64 KB data caches, QIO flash. Small gains each.
- Memory on the board (debug mode, printer attached, idle): internal 92 KB free (48 KB largest block), PSRAM 573 KB free after the 7.5 MB shared buffer. Per-line print buffers come from internal RAM (`BJL_MALLOC_FAST`), Canon block buffers from PSRAM (`BJL_MALLOC_BULK`). The lowest free internal RAM seen during a 600 dpi job is about 67 KB. IPP connection threads have 12 KB stacks and use about 3.5 KB.
- The print conversion loop yields every 64 lines (`vTaskDelay(1)`). Without that, the task watchdog fires.

## Gotchas

- QEMU cannot emulate octal PSRAM; `CONFIG_SPIRAM_IGNORE_NOTFOUND=y` lets the firmware boot without it. So in QEMU everything is internal RAM.
- QEMU does not emulate the quad I/O read command: with QIO, direct flash reads (`esp_partition_read`: OTA image check, core dump) return garbage while mmap reads work. The qemu env builds with DIO (`sdkconfig.defaults.qemu`); the board keeps QIO.
- PlatformIO's `board_build.flash_mode` only affects the uploader. QIO is set by `CONFIG_ESPTOOLPY_FLASHMODE_QIO` (the header still reads "dio", which is expected on the S3).
- After renaming or removing a source file, PlatformIO may still build the old one from its cached CMake configuration ("Source ... not found"): delete `.pio/build/<env>/CMakeCache.txt`.
- Sockets: `CONFIG_LWIP_MAX_SOCKETS=28` covers IPP (8 connections + 2 listeners), mDNS, SNTP, the debug server (3 + listener + control), the log stream (listener + client) and 4 event listeners, with a little room.
- The ESP-IDF WiFi driver logs the SSID at info level. Its log level is set to warn so the network name doesn't end up in logs.
- The app partitions start at `0x20000` (OTA layout); the bootloader with rollback is 22.6 KB (limit 32 KB before the partition table at 0x8000).
- A serial port can only be opened by one program: a log reader from another session blocked a USB flash ("device reports readiness to read but returned no data").
- Shell (zsh) traps when scripting: unmatched globs abort the command (`setopt null_glob`), there is no `timeout`, `log` is a builtin, `$VAR` holding a command with arguments is not split, and macOS `sed` has no `\b` (use perl).

## Investigated and parked

- AirDrop from the board (ESP32Drop, https://github.com/s-iwaki-d/ESP32Drop, 0BSD): a working AWDL + AirDrop implementation for ESP32-S3 with PSRAM, mostly ESP-IDF code (Arduino only in the BLE part). It can list nearby AWDL peers with an average RSSI and leaves the choice to the caller (its example takes the strongest above -30 dBm, "phone in hand"; -43 across the room). Against it here: AWDL cannot share the radio with the WiFi station (and the router is on another channel than AWDL (6)), so every send takes the board off the network for 30-60 s; BLE wake-up needs about 26 KB of internal RAM and TLS two 16.6 KB contiguous internal blocks; only files under 128 KiB are confirmed to reach an iPhone; receivers must be in "Everyone" mode and see a preview, and the receiver's name is not decoded yet. The user chose the web page for the iPhone instead.

## Limitations and ideas

- Printing: plain paper only (no photo media, no borderless). A4/Letter only. No copies (clients repeat the pages), no duplex, no JPEG/PDF over IPP (the web UI renders PDFs and pictures itself), no gzip, no IPPS, no authentication, IPv4 only. WiFi settings are compiled in. The colour tuning (dot gain 0.25 CMY / 0.15 K, full black generation) has not been checked on paper yet.
- Web UI: printing a photo at 600 dpi sends about 10 MB per page, and a page only starts printing once all pages are rendered (one request). pdf.js gets no CMaps or wasm decoders (rare CJK fonts without embedding and JPEG 2000 images will not render).
- Ideas: IPv6 (faster `.local` resolution on macOS); a token for OTA; finishing the iPhone web flow; buffering converted pages in PSRAM so print clients can disconnect early; an SD card for large spools (pinout in `docs/sd_card_pinout.png`).
